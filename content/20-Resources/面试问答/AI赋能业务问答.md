# 最有料2

# 一、你怎么理解“AI赋能业务”？你过去有没有实际做过？

这个问题我认为是**高概率问题**，因为它直接对应 JD 第2条。

### 第一层：先理解业务，而不是先上AI

我理解AI赋能业务，第一步不是先决定用RAG还是Agent，而是先看业务流程里面哪些环节真正存在效率瓶颈。

我一般会先看三个方面：

**第一是重复性工作。**比如大量人工查询、整理、录入。

**第二是信息处理。**比如企业内部有大量文档、知识、历史数据，但是人员需要花很多时间去检索和理解。

**第三是决策辅助。**比如原来需要人工根据多个数据源进行判断，这类场景可以考虑让AI参与分析。

所以我理解AI项目首先应该解决的是**业务问题，而不是技术问题**。

### 第二层：再判断AI适不适合

确定场景之后，我会进一步判断这个问题到底适不适合AI。

如果是规则非常明确、结果必须100%确定的流程，我不会为了AI而AI，可能直接通过规则引擎或者传统系统解决。

如果涉及大量非结构化知识、自然语言理解、信息总结、辅助决策，这类场景AI的价值会比较明显。

比如企业知识库，我会考虑RAG；如果需要AI自己调用多个系统、执行多个步骤，我才会进一步考虑Agent。

所以我的原则是：**先业务价值，再技术方案。**

### 第三层：最终要看业务结果

AI真正上线以后，我认为还要解决一个问题，就是怎么证明它真的有效。

所以我会给AI项目设置一些可以量化的指标，比如人工处理时间、任务完成时间、人工介入率、回答准确率以及使用率等。

最终不是说“我们上线了一个AI助手”，而是要能够回答：

**原来需要多少时间，现在需要多少时间；原来多少人工，现在减少了多少人工；原来的流程是什么，现在发生了什么变化。**

我认为只有能够量化到业务结果，AI项目才真正有价值。

# 二、如果让你负责公司AI产品从0到1，你会怎么做？

这个问题非常重要，因为 JD 明确写了：

**AI Native产品或项目从0到1优先。**

### 第一层：先定义问题

如果让我负责一个AI产品从0到1，我不会一开始就确定技术架构，而是先把业务问题定义清楚。

我会先明确三个东西：

**谁在用、解决什么问题、成功标准是什么。**

比如是给销售使用，还是给研发使用；是减少人工查询，还是提高内容生产效率。

只有这个问题明确了，后面才能判断到底应该做RAG、Agent还是普通AI能力。

### 第二层：做最小闭环

第二步我会优先做一个最小可用版本，而不是一开始把系统做得特别复杂。

比如如果是企业知识助手，我可能先实现：

**知识接入 → 文档解析 → 向量检索 → RAG回答 → 用户反馈**

先让业务真正用起来。

如果是Agent，则先把最核心的一两个工具接进去，比如查询业务数据或者调用内部系统。

先验证AI能力到底能不能解决实际问题。

### 第三层：验证之后再工程化

MVP验证有效以后，我才会重点考虑工程化问题，比如权限、安全、知识更新、模型管理、调用成本、监控、日志以及稳定性。

同时根据用户反馈不断调整Prompt、知识库和Agent流程。

最后再把这个能力真正嵌入业务系统，而不是让员工额外打开一个AI工具。

我理解AI产品从0到1最重要的其实是：

**业务问题 → 最小闭环 → 数据验证 → 工程化 → 规模化。**

# 三、你怎么推动团队使用Codex、Claude、Cursor这些AI Coding工具？

这个问题和 JD 第3、4、5条高度匹配，**我认为也是高概率问题。**

### 第一层：先解决“大家为什么不用”

我推动AI Coding的时候，最开始发现的问题其实不是工具不会用，而是团队成员不知道**AI到底应该怎么进入研发流程**。

如果只是告诉大家“以后多用Cursor、Claude或者Codex”，最后很容易变成每个人自己摸索，效果差异非常大。

所以我第一步不是强制工具，而是先把研发过程拆开，看哪些环节最适合AI介入。

### 第二层：建立 AI 研发 SOP

我会把 AI 介入研发流程分成三个阶段，核心思路是让 AI 从**方案设计一直参与到知识沉淀**，而不是只用来写代码。

**① 方案阶段：从需求到设计**

需求阶段先让 AI 辅助分析需求，补充边界条件、异常场景和技术风险；进入设计阶段以后，可以让 AI 根据需求辅助输出技术方案、接口设计、数据库设计以及时序流程，再由开发人员结合实际业务进行评审和确认。这样可以把 AI 的作用从“写代码”提前到“怎么设计”。

**② 开发阶段：从编码到质量**

进入开发以后，让 AI 辅助代码生成、代码重构、问题排查和单元测试；测试阶段让 AI 根据需求和代码自动补充测试用例、异常场景和边界条件；开发完成以后，再让 AI 做第一轮 Code Review，比如检查空指针、异常处理、SQL、并发以及代码规范等，最后由人工进行最终确认。

**③ 沉淀阶段：从交付到知识资产**

项目交付以后，我会要求把 AI 在开发过程中产生的有价值内容沉淀下来，比如技术方案、Prompt 模板、常见问题、优秀代码案例、故障处理经验以及项目上下文，逐渐形成团队自己的 AI 知识库和任务模板。这样下一次遇到类似需求，就不是重新让 AI 从零开始，而是可以复用之前的经验。

最终我希望形成的是一条完整的链路：**需求分析 → 方案设计 → AI辅助开发 → 测试 → Review → 交付 → 知识沉淀。**

同时把 Prompt 规范、项目上下文、代码规范和常见任务模板标准化，让 AI 从个人工具逐渐变成团队统一的研发能力。

### 第三层：最终用数据证明效果

最后我认为一定要数据化。

比如可以统计需求从开发到测试的周期、代码生成比例、测试用例生成情况、Review问题数量以及人均交付效率。

当然AI生成的代码不能简单按照代码行数衡量，因为代码越多不一定效率越高。

我更关注的是**研发周期有没有缩短、重复劳动有没有减少、质量有没有下降、团队整体交付能力有没有提升。**

我认为AI Coding真正落地的关键不是“买了多少工具”，而是：

**工具 → SOP → 团队习惯 → 数据验证。**

# 四、如果团队有人不愿意使用AI，你怎么办？

这个问题很适合技术经理岗位。

### 第一层：先找原因

我不会一开始就要求所有人强制使用。

因为团队成员不用AI，原因可能完全不同。

有的人是不会用，有的人担心生成代码质量，有的人觉得自己效率已经比较高，还有的人可能是担心AI影响自己的工作。

所以我会先区分问题，而不是统一强制。

### 第二层：从低风险场景开始

我会先选择一些比较容易验证的场景，比如代码解释、单元测试、SQL分析、文档生成、代码Review。

这些场景对原有代码风险比较低，而且效果容易比较。

让团队成员先看到AI确实能够减少一些重复工作，而不是一开始就让AI直接修改核心业务。

### 第三层：从个人能力变成团队机制

当大家逐渐接受以后，再把有效的方法沉淀成团队SOP，比如什么场景必须使用AI辅助，什么场景必须人工Review，哪些代码不能直接交给AI。

最终我希望形成的是：

**不是要求大家“用AI”，而是让团队形成“知道什么时候用AI、怎么用AI、怎么控制风险”的能力。**

这样AI才真正成为团队能力，而不是某个人的个人技巧。

# 五、你怎么设计AI研发效能的考核机制？

这个问题几乎就是 JD 第4条原话，**非常值得准备。**

### 第一层：不能只考核“AI使用次数”

我认为AI考核不能简单看一个人用了多少次AI，或者生成了多少代码。

因为这些指标很容易失真。

比如一个人生成了很多代码，不代表他的效率一定更高，甚至可能产生更多Review和返工。

所以我会从**效率、质量、使用程度**三个方面来看。

### 第二层：建立指标体系

效率方面，可以看需求交付周期、开发耗时、测试耗时以及人均交付量。

质量方面，可以看缺陷率、Review问题、线上问题以及返工率。

AI使用方面，则可以看AI辅助任务覆盖率、AI生成测试用例比例、AI辅助Review覆盖率等。

但是这些指标不能单独看，而是要组合起来。

### 第三层：最终看业务结果

最终我认为最重要的还是结果。

比如一个团队AI使用率很高，但是交付周期没有下降，质量还下降了，那说明AI流程设计本身就有问题。

所以我更倾向于建立：

**AI使用数据 → 研发效率 → 质量数据 → 最终业务交付结果**

这样才能真正判断AI是不是产生了价值。

# 六、你怎么理解RAG和Agent？公司什么场景适合用？

这个属于**AI技术深度题**，技术经理很容易被问。

### 第一层：先区分解决的问题

我理解RAG和Agent解决的问题不一样。

**RAG主要解决的是知识获取问题。**

企业有大量内部知识，模型本身不知道或者知识不是最新的，这时候通过检索企业知识，再让模型基于检索结果回答。

**Agent解决的是任务执行问题。**

不只是回答问题，而是能够根据用户目标进行任务拆解，然后调用工具或者系统完成操作。

### 第二层：结合实际业务判断

比如企业内部制度、产品文档、技术文档、项目资料，这类场景我会优先考虑RAG。

如果用户说：

“帮我查询某个客户最近的订单，然后分析一下异常情况，再生成一份报告。”

这时候就不只是知识检索了，需要AI调用数据库或者业务接口，再进行分析和输出，这种场景更适合Agent。

### 第三层：真正落地还要考虑风险

但是Agent相比RAG复杂很多，因为它涉及工具调用、权限、安全以及错误执行的问题。

所以我不会一开始就让Agent拥有大量系统权限，而是会按照**最小权限、工具白名单、操作审计以及人工确认**的方式逐步开放。

我理解企业AI落地最重要的是：

**RAG解决“知道什么”，Agent解决“做什么”。**

# 七、如果让你负责公司的AI产品，你怎么保证AI回答准确？

这个问题也很常见，而且非常能体现你的架构思维。

### 第一层：先解决数据问题

我认为AI准确性首先不是Prompt问题，而是数据问题。

如果知识库里面的数据本身就是错误的、过期的或者重复的，那么模型再强也很难保证结果。

所以第一步需要做好知识来源、数据清洗、切片、版本以及权限管理。

### 第二层：解决检索和模型问题

第二步才是RAG本身。

比如优化Chunk切分、Embedding模型、检索策略、TopK、Rerank等。

如果只是向量相似度检索，有时候会召回语义相似但真正不相关的内容，所以需要结合关键词检索或者Rerank提高召回质量。

最后再让模型基于可靠上下文生成答案。

### 第三层：建立反馈闭环

最后不能认为上线以后就结束了。

我会收集用户反馈，比如哪些问题回答错误、哪些问题没有找到知识、哪些回答需要人工修改。

再把这些问题回流到知识库、检索策略和Prompt中。

所以整个链路应该是：

**数据质量 → 检索质量 → 模型生成 → 用户反馈 → 持续优化。**

# 八、如果让你负责一个AI项目，你怎么推动跨部门落地？

这个问题对应 JD 第5条：

**跨部门协同，推动产品快速从方案到落地。**

### 第一层：先统一目标

我认为跨部门协作最容易出现的问题，就是大家关注的目标不一样。

产品关注体验，业务关注结果，技术关注可实现性，AI团队可能关注模型效果。

所以项目开始的时候，我会先把目标统一成一个业务结果。

比如不是说“做一个AI助手”，而是说：

**把某个业务流程从原来的30分钟降低到5分钟。**

### 第二层：明确边界和责任

然后把整个项目拆成几个部分：

**业务流程、产品体验、AI能力、系统开发、数据和验收指标。**

每一部分明确负责人和交付标准。

AI部分也不会无限追求模型效果，而是需要结合整体业务目标确定一个可接受的效果。

### 第三层：快速验证

我比较倾向于先做小范围试点，而不是所有部门一起上线。

先选择一个真实业务场景做POC，验证AI效果和业务价值。

如果数据证明有效，再扩大范围。

这样可以减少跨部门协作成本，也能够快速发现问题。

最终形成：

**业务目标 → 小范围验证 → 数据反馈 → 快速迭代 → 全面推广。**

# 九、如果让你搭建公司的AI技术体系，你会怎么做？

这个问题更偏**技术经理/架构负责人**。

### 第一层：基础能力统一

我不会让每个业务团队自己去接模型。

首先会考虑建设统一的AI基础能力，比如模型接入、Prompt管理、Token统计、调用日志、权限以及基础监控。

这样不同业务使用AI的时候，不需要重复建设。

### 第二层：知识和Agent能力平台化

第二层是把通用能力抽出来，比如RAG知识库、Embedding、Rerank、Agent工具调用、工作流等。

业务团队只需要关注自己的业务场景，而不是每个项目都重新搭一套AI基础设施。

### 第三层：治理和数据化

最后需要考虑AI治理。

比如模型效果、调用成本、Token消耗、用户使用情况、回答质量以及安全审计。

这样技术团队才能知道：

**哪些AI能力在使用、成本多少、效果怎么样、哪些场景值得继续投入。**

我认为企业AI平台最终应该形成：

**统一模型能力 + 统一知识能力 + 统一Agent能力 + 统一治理能力。**

# 十、你怎么看现在外部大模型发展这么快，公司应该怎么选择模型？

这个问题对应 JD 第6条。

### 第一层：不绑定单一模型

我不会让公司一开始就深度绑定某一家模型。

因为现在模型更新非常快，今天效果比较好的模型，几个月以后可能就会发生变化。

所以从架构上应该把模型和业务解耦。

### 第二层：根据场景选择

不同模型解决的问题也不一样。

比如复杂推理可能选择能力更强的模型，普通文本处理可以选择成本更低的模型，企业内部某些敏感数据可能还要考虑私有化部署。

所以我更关注：

**效果、成本、延迟、数据安全以及部署方式。**

### 第三层：建立模型评测机制

最后不能单纯凭感觉选择模型。

我会建立一套企业自己的测试数据集，把常见业务问题固定下来，然后比较不同模型的准确率、响应时间和成本。

这样以后模型更新了，也可以重新测试。

所以我的思路是：

**模型可替换 + 场景化选择 + 持续评测。**

# 十一、你作为技术经理，怎么平衡业务快速交付和技术架构？

这个问题虽然 JD 没有直接写，但**技术经理非常容易被问**。

### 第一层：先区分核心和非核心

我不会追求所有东西一开始就做到最完美。

我会先区分哪些是核心业务能力，哪些是可以快速验证的部分。

核心能力比如数据模型、权限、安全、核心交易流程，这些设计的时候需要更加谨慎。

一些试验性AI能力，可以先快速做POC。

### 第二层：控制技术债

快速交付不等于完全不考虑架构。

我会尽量保证核心边界和接口设计稳定，把变化比较大的部分隔离出来。

这样第一版可以简单，但未来还有演进空间。

### 第三层：根据业务价值决定投入

我最终判断一个技术方案值不值得投入，不是看技术本身先进不先进，而是看它对业务有没有价值。

如果一个技术方案很漂亮，但是业务价值很低，我不会投入大量资源。

如果一个业务已经证明有价值，那我会逐步把它从POC升级成正式的平台能力。

我理解技术经理最重要的能力之一，就是在**速度、质量和长期架构之间找到平衡。**

# 十二、如果你加入我们，前90天你会怎么做？

这个问题我建议你**一定准备**。

### 第一层：先理解业务和团队

如果我加入，我不会第一天就开始改技术架构。

前期我会先了解公司的核心业务、产品流程、研发团队以及目前的技术体系。

同时重点找几个业务流程，看看哪些地方存在明显的人工成本和效率瓶颈。

### 第二层：找到AI切入点

然后我会筛选几个AI场景。

我会优先选择**价值比较明确、数据基础比较好、实施风险比较低**的场景做POC。

比如知识检索、内容生成、研发辅助或者业务数据分析等。

先证明AI确实能产生价值。

### 第三层：形成标准化能力

如果验证有效，我会进一步把成功经验沉淀下来。

包括AI研发SOP、工具规范、Prompt规范、评测指标以及团队培训体系。

最终希望不是只做一个AI项目，而是让团队逐渐具备持续发现和落地AI场景的能力。

所以如果用三个阶段概括，就是：

**先理解业务 → 再验证场景 → 最后形成体系。**
