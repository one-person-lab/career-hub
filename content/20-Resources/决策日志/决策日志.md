# 决策日志

> 记录「当初为什么这么定」。半年后回来看，最怕的不是不知道改成什么，而是忘了当初的理由然后推翻已有结论。

## 格式

每条六项：`日期 / 决策 / 理由 / 被否决的方案 / 影响范围 / 未决`

---

## 2026-09-11 · 职业工作台采用「成果为唯一事实源」而不是「岗位优先」

- **决策**：工作台的核心对象是**成果**（`EX-xxx`），不是岗位。简历、故事库、自我介绍、作品集全部是从成果卡派生的视图。
- **理由**：市面上的求职工具（Teal / Huntr / Simplify）都是岗位优先 —— 因为它们假设你在高频海投。但投递量小的时候，瓶颈不在「管不过来」，而在「同一段经历要写三遍还互相不一致」。先解决复用，再解决管道。
- **被否决**：① 做一个投递看板（Kanban）—— 对个位数投递量是负担，不是帮助；② 做个题海（LeetCode 式）—— 那是题库型产品的活，不是个人工作台该做的事。
- **影响范围**：数据模型、项目成果视图、面试问答的写法
- **未决**：以后如果转到高频投递（一个月 20+ 家），要不要补一个管道视图？

## 2026-09-11 · 骨架先立，内容后填

- **决策**：不把 `career-os/` 的现有内容迁移进来，只做**只读盘点**（总览页显示还有多少篇待挑）。先把结构与字段规范立住。
- **理由**：旧库是两年里逐步长出来的，格式不统一、有重复副本。直接导入会把旧结构固化进新工作台，「用很脏的数据做出来只会更乱」。
- **被否决**：边搭界面边迁移内容 —— 迁移时会被旧格式牵着走，设计就成了将就。
- **影响范围**：`content/` 全部为新写；`../career-os/` 仅用于统计
- **未决**：迁移顺序？先项目成果还是先知识点？

## 2026-09-11 · 专属视图只做三个

- **决策**：只给 `总览` / `项目成果` / `知识点` 写专用界面，其余板块全部走通用 md 渲染器。
- **理由**：按 md-vault-workbench 的 A/B 分层 —— 结构型资产（卡片墙、图谱）做扎实，其余只做薄渲染。通用渲染器覆盖 80% 的场景，且**加一个目录就等于加一个板块，不用改代码**。
- **被否决**：给每个板块都写专属视图 —— 维护成本高，且产品结构一调整就全废。
- **影响范围**：`src/views/` 四个文件
- **未决**：`公司准备` 以后要不要做成时间线/漏斗视图？

## 2026-09-11 · 工作台放在 `career-hub/` 而不是 `career-os/` 内部

- **决策**：与 `media-hub`、`product-hub` 并列作为独立工作台仓库，通过只读映射读 `../career-os/`。
- **理由**：`career-os/` 是独立 git 仓库且已在远端。把 npm 工程放进去会把 `node_modules` 和构建产物推进仓库；且它与另两个工作台受众不同、数据源不同。
- **被否决**：放进 `career-os/workbench/` —— 需要额外 gitignore 且会让那个仓库变重
- **影响范围**：`vite.config.ts` 的 `portfolioStatic()` 映射、相对路径
- **未决**：三个工作台要不要统一成一个入口（一个壳子切换三套数据源）？
