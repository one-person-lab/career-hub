# 分布式事务

事务的 ACID

原子性 Atomicity 要么全做 要么全不做（回滚）

一致性 Consistency 数据状态保持一致（转账场景）

隔离性 Isolation 并发事务互不干扰（AB 互不影响）

持久性 Durability 提交后永久生效（写入磁盘）

​  

2PC Two Phase Commit 两阶段提交 强一致性方案

第一阶段执行 第二阶段提交 如果第一阶段执行有人不成功，则全部回滚

致命问题：

1、同步阻塞/锁

2、事务协调者单点故障

3、Commit 过程挂了，导致数据不一致

​  

3PC Three Phase Commit 三阶段提交 改进版的 2PC

多了第一步资源检查，如果资源不够直接就不执行，引入超时机制

问题：

更高的复杂度和性能开销

和 2PC 存在一样的故障问题

​  

TCC Try Commit Cancel 补偿型事务 最常见的分布式事务方案

尝试执行，预留资源

确认执行，使用资源（如果多次失败，记日志，人工介入）

取消执行，释放资源

相比 2PC 性能更高，数据不会被长时间锁住

可以跨数据资源，MySQL、Redis 都支持回滚，2PC 只能数据库

要求：

幂等性 Confirm 和 Commit 可以重复执行

最终一致 失败了重试，直到成功

问题：

开发成本高

业务侵入强

逻辑复杂

​  

可靠消息最终一致性

基于 MQ 的异步解耦方案，业务侵入最小

增加消息表，并且定时任务兜底

消费者重试，重试多次失败，进入死信队列

幂等性，消息去重，业务唯一 ID，状态机防止重复处理

消息状态

​  

Saga 模式，长事务补偿

需要补充反向补偿方法

问题：

没有隔离性，中间状态可能被其他事务看到，比如创建了订单又取消

补偿复杂，而且必须保证幂等

CAP 定理 分布式系统的铁三角 三者不可兼得，只能选其二

Consistency 一致性 读操作总能读到最新写入的数据

Availability 可用性 每个请求都能得到响应

Partition Tolerance 分区容错性 网络分区时系统仍能工作

CP 放弃可用性（金融转账、交易支付、库存扣减）

AP 放弃一致性（用户评论、点赞收藏、商品浏览）

​  

BASE 理论 CAP 的实践方案 互联网公司的普遍选择

BA Basically Available 基本可用 允许损失部分可用 限流降级增加响应时间

S Soft State 允许数据存在中间状态（订单处理中、支付确认中、同步进行中）

E Eventually Consistent 最终一致性（异步同步、消息重试、定时对账）
