# SpringCloud

#### **Spring Cloud 组件有哪些？**

Spring Cloud是一套基于Spring Boot完整的微服务解决方案，换句话说，提供了构建分布式系统所需的全家桶。

-   注册中心 Nacos

-   服务注册：服务提供者需要把自己的信息注册到Nacos，比如服务名称、IP、端口
-   服务发现：服务消费者定时从Nacos拉取pull服务列表，如果有集群，利用负载均衡算法选择一个发起调用
-   服务监控：默认是临时实例，临时实例会会每隔一段时间向Nacos发送心跳，报告健康状态，如果一定时间没收到心跳，则剔除，如果是非临时实例，则Nacos会主动询问健康状态，但是非临时实例不会被剔除，如果服务提供者地址发生变更，Nacos会主动推送push变更信息
-   Nacos集群：Nacos集群默认采用AP模式，当集群存在非临时实例时，采用CP模式

-   AP模式强调高可用性和分区容忍性，这种模式下，Nacos集群可以容忍网络分区，即部分节点之间失去了联系，集群仍然能够继续工作，所以数据可能存在不一致，但是至少保证可用
-   CP模式强调一致性和分区容忍性，这种模式下，Nacos集群会保证数据的一致性，即使发生了网络分区，这可能导致某些情况下的写入操作失败

-   远程调用 Feign
-   负载均衡 Ribbon

-   发起远程调用Feign就会使用Ribbon

微服务发起远程调用，会经过Ribbon，Ribbon会去注册中心拉取服务信息，然后轮询到某一台服务

#### **Spring Cloud和Dubbo的区别？**

Dubbo基于RPC，采用面向接口的编程风格，服务提供方实现接口，服务消费方通过接口调用服务。

Spring Cloud基于REST，采用声明式的编程风格，服务提供方通过HTTP暴露REST接口，服务消费方通过HTTP调用服务。

Dubbo更像是一个组装机，它的核心是提供了服务治理的功能，但是其他的组件需要自己去适配，比如说网关、配置中心、批量任务、服务追踪、消息总线，但是Spring Cloud更像是一个品牌机，它把微服务架构所需要的组件都组装好了，开箱即用。

#### **在分布式系统中，你是如何处理分布式事务和一致性的？**

在项目中，主要采用基于消息的最终一致性方案，当涉及到多个服务的数据更新时，先发送消息到消息队列，然后由各个服务消费消息并执行相应的数据更新操作，这样可以保证最终数据的一致性。

在示例项目B中，当时做时光集相册订单支付的时候，就是这样的场景，当时主要涉及到订单服务、库存服务、支付服务，当用户下单时，需要在订单服务中创建订单，然后根据商品的库存情况来更新库存服务的库存信息，然后最后才完成支付，如果一步出错就可能导致数据不一致。

当用户发起提交订单时，订单服务接收到请求，则将订单信息写入消息队列，支付服务监听订单支付的消息，一旦收到支付信息，支付服务开始处理支付请求，这时候就需要进行事务补偿机制，当支付服务出现异常时，会发送补偿消息到消息队列，其他服务监听补偿信息相当于回滚信息，通过补偿操作来保持支付和订单状态的一致性。并且在支付服务中引入幂等性设计，避免重复支付。

#### **如何解决服务雪崩？**

-   超时处理：请求超过一定时间没有响应就返回错误信息，不会无休止的等待，起到缓解的作用
-   舱壁模式：限定每个业务能使用的线程数，避免耗尽整个tomcat线程池的资源，因此也叫线程隔离
-   熔断降级：断路器会统计异常比例，超出阈值触发熔断，拦截访问问题服务一切请求
-   流量控制：控制访问的QPS，避免服务因为服务请求突增导致故障

#### **分布式服务接口幂等问题？**

幂等场景

-   用户重复点击
-   MQ消息重复
-   应用使用失败重试机制

接口幂等

-   PUT请求，如果以绝对值更新，是幂等的，如果是增量的方式更新，不是幂等的
-   POST请求，请求多次造成的结果不同，不是幂等的

-   解决方式

-   数据库唯一索引
-   token+redis

-   第一次请求获取token，redis存储token，返回给前端token
-   第二次请求带上token，验证token是否存在，存在则处理业务并删除token，不存在就返回

-   分布式锁

-   在更新的操作的时候加锁，要控制好锁的粒度，性能较低

#### **RPC是什么？**

Remote Procedure Call，远程过程调用。RPC实现了在不同机器上运行的程序之间的通信，RPC隐藏了底层的网络通信，给开发提供了更简单的分布式计算接口。

#### **REST是什么？****你对RESTful规范的理解？**

REST，Representational State Transfer，表现层状态转移。它是一种软件架构风格，RESTful是这种设计风格的实现，RESTful把所有事物都看作资源，使用URI表示，通过HTTP方法操作资源，GET用来获取数据，POST用来新建资源，PUT用来更新资源，DELETE用来删除资源。架构清晰、符合HTTP规范、扩展性好、可实现缓存。

#### **Feign的调用过程？**

Feign是一个声明式的Http客户端，可以优雅的实现Http请求的发送，简化我们发起远程调用的代码。

通过@EnableFeignClients开启Feign功能。基于SpringMVC的注解来声明远程调用的信息，远程调用就会变得跟本地调用一样简单。同时Feign集成了Ribbon，实现了负载均衡，Feign默认没有失败重试机制，使用的Ribbon的重试机制。

Feign的优化主要是在日志优化和连接池优化，使用HttpClient或OKHttp代替URLConnection。

使用RestTemplate调用，它是Spring框架中的一个类，它简化和标准化Http通信的方式，不需要手动处理Http连接、数据流序列化等细节。它支持不同类型的Http请求和响应，支持请求和响应数据与Java对象进行转换。不过RestTemplate的写法不够优雅，因为要维护Url并且复杂的参数难以维护。Feign在此基础上做了简化。

通过它的概念就知道，它就是用来简化我们发起远程调用的代码的。我们以前要进行远程调用，需要去构建http请求url，填写http请求头信息，填写报文等繁琐的操作。使用feign的话，远程调用就会变得跟本地调用一样简单。同时feign还整合了ribbon用来实现负载均衡，整合了hystix实现服务熔断。

#### **Sentinel如何做熔断限流？QPS设置的值是如何定的？**

QPS需要根据服务器资源，性能测试结果，实际负载情况来确定。

Sentinel用于生产前，进行全面的性能和压力测试。通过模拟实际的负载和异常情况，可以确定适当的熔断和限流规则，一旦启用，要监控熔断和限流情况，根据监控数据，动态调整熔断和限流规则，以应对不断变化的负载和异常情况。

#### **Feign的最佳实践？**

1.  通过继承的方式

给消费者的FeignClient和提供者的Controller 定义统一的父接口作为标准，Controller去实现接口，消费者直接继承接口调用。但是这个会造成紧耦合，而且SpringMVC的特殊参数没办法直接实现，比如PathVariable，不推荐使用。

1.  通过抽取的方式

将FeignClient抽取为独立模块，并把接口相关的POJO，默认的Feign配置都放在这个模块，提供给所有消费者调用。但是会造成引入没必要的方法。

#### **降级和熔断？**

嗯，在做示例项目B时，每当开学季都是系统的高负载时期，这个时候就会使用降级，为了保护核心功能的可用性，主动放弃部分非核心功能以减少负载，防止系统崩溃或长时间无响应，从而影响用户体验。

嗯，熔断的目的是防止故障的服务影响整个系统服务雪崩，并且服务恢复正常后，会逐渐恢复对服务的调用，以保证系统的稳定性和可用性。当在一段时间内的请求失败率超过一定的阈值，熔断器会进入熔断状态，断开对服务的请求。保持一段时间熔断状态之后，会进入半开状态，允许部分请求发送到服务，以检测服务是否恢复正常。如果服务正常运行，熔断器会切换到关闭状态，允许所有请求正常通过。

目前使用的是Sentinel。

#### **你们项目中有没有做限流，怎么做呢？**

为什么要做限流？

-   并发的确大（突发流量）
-   防止用户恶意刷接口

什么情况下限流，需要说明QPS具体多少？

以前做过刷视频获取金币的接口，就有遇到恶意攻击，为了保证系统正常允许，就根据压测的QPS结果来设置限流。

在以前我们做幼儿园的成长时光集，有做抢优惠券活动，QPS高达2000，为了应对突发流量，需要做限流。

限流的实现方式？

-   Nginx 漏桶算法：limit\_req\_zone = serviceRateLimit

Nginx可以控制速率，用到的就是漏桶算法，就是将请求放入桶中，按照一定速率流出，如果满了就抛弃

-   网关 令牌桶算法：RequestRateLimiter结合Redis使用

在SpringCloudGateway中支持局部过滤器RequestRateLimiter来做限流，使用令牌桶算法，以固定的速率生成令牌，存入令牌桶，桶满后暂停生成，请求需要到令牌桶申请令牌，申请到令牌的才能请求

可以根据IP或路径进行限流，可以设置令牌每秒填充平均速率，和令牌桶总容量

key-resolver：定义限流对象（IP、路径、参数）

replenishRate：令牌桶每秒填充平均速率

burstCapacity：令牌桶总容量

-   自定义拦截器

嗯，限流其实跟生活中的排队是一个效果的，避免过多的人导致事故。在程序中有几种算法来实现限流：

固定窗口计数器算法，它规定了我们单位时间处理的请求数量，但是这种算法无法保证限流速率。

滑动窗口计数器算法，它把时间以一定比例分片，限制每秒的请求数。

漏桶算法：消息队列的实现机制，将请求放入桶中，在按一定速率流出水。

令牌桶算法：以固定速率生成令牌，拿到令牌的才能发起请求。

单机限流可以使用guava的基于令牌桶算法实现的RateLimiter工具类。

分布式限流可以使用中间件Sentinel或者Redis+Lua的实现方式。

嗯，这个要基于系统的架构，如果有Api网关可以直接网关作限流最简单直接，如果没有网关，可以使用redis基于令牌桶算法实现，它基于一个桶，桶中放入一定数量的令牌，每个令牌代表一个请求的许可，每个请求会消耗一个令牌，系统会以固定速率放入令牌，如果桶中没有足够的令牌，则请求会被拒绝。

#### **什么是Gateway网关？**

网关可以用来做统一身份认证和权限检验，还有服务的路由和负载均衡，请求限流。

Zuul是基于Servlet的实现，属于阻塞式编程。Spring Cloud Gateway是基于Spring5中提供的WebFlux，属于响应式编程的实现，具有更好的性能。

网关的搭建步骤：

1.  配置nacos注册地址，编写路由配置，根据配置的路由去过滤分发请求，通过断言工厂，判断用户的请求

spring: cloud: gateway: routes: - id: uri: lb://微服务名称 predicates: # 断言 - Path=/user/** filters:

1.  在通过断言后，会进入路由过滤器，可以对进入网关的请求和微服务的响应做处理
