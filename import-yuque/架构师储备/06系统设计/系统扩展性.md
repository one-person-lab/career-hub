# 系统扩展性

目标：学习提高系统扩展性的策略，有助于更高效的迭代系统

今天我们接着系统设计铁三角系列分享。这个系列将涵盖三个核心方面：扩展性、性能和稳定性。上一次，扩展性让系统更加强大，性能让系统更加高效，稳定性让系统更加可靠。

我们首先探讨系统设计铁三角中的一个关键概念——扩展性。无论是初创公司还是成熟企业，系统的扩展性都是成功的关键因素之一。它关系到我们的系统能否在用户量增加、数据量增长、功能需求变更等情况下，依然保持稳定和高效。

# **一、可扩展性的介绍**

## **1.1 可扩展性的重要性**

扩展性是指系统能够应对增长的能力，包括用户数增加、数据量增加、流量变化以及功能需求变化等。一个具有良好扩展性的系统在面对这些变化时，性能不会显著下降，且能够通过添加资源（如服务器、存储等）来提升性能，且降低迭代的成本。

### **1.1.1 业务扩展**

良好的扩展性使系统在业务扩展时能够迅速响应需求，而无需大规模重构或在已有复杂业务逻辑中不断累积代码，从而降低系统风险。

### **1.1.2 数据增长**

随着业务的发展，用户数和数据量会不断增加。一个可扩展的系统能够支持业务的快速增长，确保业务运作的连续性。

### **1.1.3** **成本控制**

通过水平扩展，可以逐步根据需求增加资源，避免一次性大规模投资，从而提升资源利用率，降低成本。此外，良好的扩展性可以减少对现有系统进行大规模重构的需求，从而降低开发和维护人员的工作量与人工成本。开发团队可以更加专注于新功能的开发和优化，而不是花费大量时间处理性能问题或代码的复杂性。

## **1.2 可扩展性的本质**

可扩展性的核心在于**占位符**的设计，也就是通过占位符来识别出扩展点。占位符是系统中用于表示和处理变化的机制，它允许系统在运行时灵活地调整和扩展，而不需要直接修改核心代码。通过合理设计占位符，系统能够适应各种变化，提高其灵活性和可维护性。

### **（1）占位符是什么**

占位符是系统中用于指示变化点的标识符，凡是可表达变化的都可称之为占位符。它表明系统中的某个部分可以根据需要进行调整或扩展。占位符使得系统在运行时能够灵活地处理变化，而不需要重新编写或修改现有代码。

-   定义：占位符是一个标识符或机制，用于表示系统中可能发生变化的部分。它标示出可以被动态配置或替换的元素，从而允许系统根据实际需求进行调整。
-   目的：通过占位符，系统可以在不修改核心代码的情况下，灵活应对需求变化、配置调整或功能扩展，提高系统的适应性和可维护性。

### **（2）占位符怎么表示**

占位符可以通过多种方式在系统中实现。每种方式提供了不同的机制来表示系统中的变化点。常见的表示方法包括：环境变量、接口、配置项、注解、事件等等。

-   **环境变量**：环境变量用于在不同环境中动态配置系统参数。它们通常在部署时设置，允许系统根据环境的不同进行适应。

**示例**：数据库地址、Nacos地址、Redis地址

DB\_URL=jdbc:mysql://localhost:3306/mydb LOG\_LEVEL=DEBUG

-   **接口**：接口定义了一组功能或服务的标准，系统可以通过不同的实现类来实现这些功能。接口的使用允许系统在运行时选择和替换不同的实现。

**示例**：通知接口、支付接口、登录接口

-   **配置项**：配置项允许系统根据配置文件中的设置动态调整功能或行为。这使得系统能够根据不同的配置需求进行调整。

**示例**：短信发送配置

-   **注解**：注解用于标识和配置特定的行为或功能。系统可以在运行时扫描和识别这些注解，并据此执行相关的逻辑，不需要侵入到方法中。

**示例**：幂等、操作日志

### **（3）占位符如何实现**

实现占位符的关键在于动态管理和调整系统中的可变部分。

-   **接口的动态实现**：定义接口并提供多个实现类，系统在运行时通过某种机制动态选择和调用具体的实现。这种方式允许系统在运行时扩展新的功能，而不需要修改已有的实现逻辑。

**示例**：

### **1.3.1 验证码组件**

验证码组件可以防止暴力登录，通过验证码组件，可以让业务方轻松集成功能，无需重复开发。

验证码存储方式：在单机部署时，验证码通常存储在本地内存中。但在集群部署中，本地存储会导致验证码无法在不同节点之间共享。因此，需要支持分布式缓存存储（如Redis）来解决这个问题。

#### **（3）SPI带来的好处**

-   **灵活性：** 可以在运行时动态选择不同的加新的存储实现，而无需修改现有代码。只需在META-INF/services中添加新的实现类即可。
-   **松耦合：** 使用接口和SPI机制实现了存储策略与业务逻辑的解耦，使得代码更清晰、易维护。
-   **开闭原则**：SPI的使用符合开闭原则（Open/Closed Principle），即系统在不修改已有代码的情况下，可以通过添加新代码来扩展功能。

### **1.3.2 幂等组件**

幂等性在分布式系统中尤为重要，因为它确保相同的操作即使被执行多次，结果仍然保持一致。通过幂等组件，可以让业务方轻松集成功能，无需重复开发。

#### **（1）识别变化点**

**唯一请求标识的生成**：不同业务场景下生成唯一请求标识的逻辑可能不同。默认情况下，可以使用请求参数作为唯一值，但这可能会有重复的风险，因此需要提供给使用方自定义的操作。

**幂等校验的策略**：针对不同的业务需求，幂等校验的策略可能需要调整。不同的业务逻辑可能需要不同的校验方式来确保幂等性。比如说超时时间、错误提示等。

**唯一标识存储方式**：用于存储和验证幂等标识的缓存或数据库策略可能有所不同。不同的应用场景可能需要不同的存储方式来确保幂等性。

#### **（2）处理变化点**

**接口设计**：定义一个统一的接口，用于生成和校验幂等标识。不同的业务逻辑可以通过实现该接口来提供不同的策略。

组件内部有自己的实现，现在需要支持用户能够自定义实现，基于Spring框架中的@ConditionalOnMissingBean条件注解，可以轻松地扩展或替换默认实现，而不需要修改框架或组件的核心代码。用户只需提供自定义实现，框架会自动使用自定义实现而不是默认实现。

public interface IdempotentKeyResolver { String resolver(JoinPoint joinPoint, Idempotent idempotent); } public class DefaultIdempotentKeyResolver implements IdempotentKeyResolver { @Override public String resolver(JoinPoint joinPoint, Idempotent idempotent) { String method = joinPoint.getSignature().toString(); String args = StrUtil.join(",", joinPoint.getArgs()); return SecureUtil.md5(method + args); } }

**条件注解**：使用Spring的@ConditionalOnMissingBean注解来实现灵活的组件替换和扩展。

@Bean @ConditionalOnMissingBean(IdempotentKeyResolver.class) public IdempotentKeyResolver defaultIdempotentKeyResolver() { return new DefaultIdempotentKeyResolver(); }

**自定义实现**：用户自己实现，就会自动替换掉原来的默认实现，达到灵活扩展。

import org.aspectj.lang.JoinPoint; public class CustomIdempotentKeyResolver implements IdempotentKeyResolver { @Override public String resolver(JoinPoint joinPoint, Idempotent idempotent) { // 自定义实现逻辑 return "customKey"; } }

#### **（3）条件注解带来的好处**

-   **灵活性**：条件注解允许根据实际情况动态加载和替换Bean。通过这种方式，系统可以在不修改现有代码的情况下，灵活地切换和扩展不同的实现。
-   **松耦合**：使用条件注解可以有效解耦组件的定义和使用。不同的实现可以独立开发和维护，互不影响，从而提高系统的模块化和可维护性。
-   **扩展性**：通过条件注解，系统可以方便地添加新的实现，而无需修改已有的代码。只需添加新的Bean实现，并通过配置或条件注解进行选择和加载。
-   **开闭原则**：条件注解的使用符合开闭原则（Open/Closed Principle），即系统在不修改已有代码的情况下，可以通过添加新代码来扩展功能。

### **1.3.3 短信组件**

短信组件是集成了多种第三方短信平台，方便业务方直接使用，无需重新对接API。

#### **（1）识别变化点**

**供应商变更**：短信服务可能由不同的供应商提供，比如百度、阿里云等。系统需要能够根据实际需求切换或扩展不同的供应商。

**消息格式**：短信的内容和格式可能需要根据不同的国家、语言或业务需求进行调整。

#### **（2）处理变化点**

**接口设计**：定义一个统一的短信发送接口，并提供不同供应商的实现。这使得系统可以在运行时选择不同的实现而无需修改调用逻辑。

public interface SmsService { void sendSms(String phoneNumber, String message); } public class BaiduSmsService implements SmsService { @Override public void sendSms(String phoneNumber, String message) { // Baidu API integration } } public class AliyunSmsService implements SmsService { @Override public void sendSms(String phoneNumber, String message) { // aliyun API integration } }

**配置文件**：通过配置文件定义短信供应商、认证方式和其他相关参数。系统可以根据配置动态选择和初始化不同的短信服务。

example: smsemail: sms: enable: true type: aliyun access-key-id: 'xxxxx' access-key-secret: 'xxxxx'

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty; import org.springframework.context.annotation.Bean; import org.springframework.context.annotation.Configuration; @Configuration public class SmsServiceConfig { @Bean @ConditionalOnProperty(name = "example.smsemail.sms.type", havingValue = "aliyun") public SmsService aliyunSmsService() { return new AliyunSmsService(); } @Bean @ConditionalOnProperty(name = "example.smsemail.sms.type", havingValue = "baidu") public SmsService baiduSmsService() { return new BaiduSmsService(); } }

**插件机制**：支持插件机制，使得可以动态添加新的短信服务供应商或发送策略。通过插件机制可以避免对系统核心代码的侵入。

添加新的短信服务供应商，正常是由组件统一添加，在组件不添加的情况下，就是使用这种插件的方式，类似SPI的方式。

#### **（3）配置带来的好处**

**灵活性**：通过配置文件的动态参数，系统可以根据不同的需求快速调整短信组件的行为。例如，更换短信服务供应商、调整发送策略等，只需修改配置文件，而无需修改代码。

**扩展性**：通过配置文件或插件机制，系统可以方便地添加新的短信服务供应商或功能。例如，当需要支持新的短信供应商时，只需添加新的配置项或插件实现，而不需要对现有代码进行大规模修改。

### **1.3.4 支付组件**

#### **（1）识别变化点**

**支付方式的多样化**：不同的支付方式（如信用卡、支付宝、微信支付等）有不同的实现逻辑和接口。

**示例**：系统需要支持添加和移除不同的支付方式，支持国内外支付方式的扩展。

**回调处理**：支付成功或失败后的回调处理逻辑可能需要根据支付方式或业务需求进行调整。

**示例**：支付成功后，需要发送通知邮件或更新订单状态。

#### **（2）处理变化点**

处理变化点的方法包括设计灵活的接口、使用策略模式和工厂模式、利用配置文件和条件注解等。这样可以帮助系统动态应对变化而不需要修改核心代码。

**接口设计**：定义统一的支付接口，不同的支付方式可以通过实现该接口来提供各自的逻辑。

public interface PaymentProcessor { PaymentResponse processPayment(PaymentRequest request); }

**策略模式**：使用策略模式实现不同的支付方式。

public class CreditCardPaymentProcessor implements PaymentProcessor { @Override public PaymentResponse processPayment(PaymentRequest request) { // 信用卡支付逻辑 return new PaymentResponse("Credit Card Payment Processed"); } } public class AlipayPaymentProcessor implements PaymentProcessor { @Override public PaymentResponse processPayment(PaymentRequest request) { // 支付宝支付逻辑 return new PaymentResponse("Alipay Payment Processed"); } }

**工厂模式**：使用工厂模式创建具体的支付处理器，通过枚举定义支付类型，避免硬编码。

public enum PaymentType { CREDIT\_CARD, ALIPAY, WECHAT, PAYPAL } public class PaymentProcessorFactory { private static final Map<PaymentType, PaymentProcessor> processors = new HashMap<>(); static { processors.put(PaymentType.CREDIT\_CARD, new CreditCardPaymentProcessor()); processors.put(PaymentType.ALIPAY, new AlipayPaymentProcessor()); // 添加其他支付方式 } public static PaymentProcessor getPaymentProcessor(PaymentType type) { return processors.get(type); } }

**配置文件**：通过配置文件定义支持的支付方式。

example: payment: alipay: access-key-id: 'xxxxx' access-key-secret: 'xxxxx'

**条件注解**：使用Spring的@ConditionalOnMissingBean注解来实现灵活的组件替换和扩展。

@Configuration public class CustomPaymentConfig { @Bean @ConditionalOnProperty(name = "example.payment", havingValue = "alipay") public PaymentProcessor alipayPaymentProcessor() { return new AlipayPaymentProcessor(); } @Bean @ConditionalOnProperty(name = "example.payment", havingValue = "credit\_card") public PaymentProcessor creditCardPaymentProcessor() { return new CreditCardPaymentProcessor(); } }

**支付处理器**：通过工厂模式在运行时选择具体的支付处理器。

import org.springframework.beans.factory.annotation.Autowired; import org.springframework.stereotype.Service; @Service public class PaymentService { private final PaymentProcessorFactory paymentProcessorFactory; @Autowired public PaymentService(PaymentProcessorFactory paymentProcessorFactory) { this.paymentProcessorFactory = paymentProcessorFactory; } public PaymentResponse processPayment(PaymentType type, PaymentRequest request) { PaymentProcessor processor = paymentProcessorFactory.getPaymentProcessor(type); if (processor == null) { throw new IllegalArgumentException("Unsupported payment type: " + type); } return processor.processPayment(request); } }

#### **（3）设计模式带来的好处**

-   策略模式

-   灵活性：策略模式允许定义一系列的算法或行为，并使它们可以互换。这使得系统可以根据需要动态选择不同的支付处理策略。
-   松耦合：策略模式将算法的定义和使用分离，使得算法的变化不会影响使用它的代码，从而提高系统的模块化程度。

-   工厂模式

-   扩展性：工厂模式通过提供一个创建对象的接口，使得系统可以根据条件创建不同的对象实例，从而使得添加新的支付方式变得简单。
-   封装性：工厂模式将对象的创建过程封装起来，调用者不需要知道具体的实现类，从而降低了系统的复杂性。

## **1.4 可扩展性的方法论**

实现系统的可扩展性需要一套完善的方法论，从具体案例进行抽象，提炼出共性的地方，就可以形成方法论，从识别变化点到使用具体实现，需要遵循一系列步骤。这些步骤包括规范、识别、注册和使用。下面将详细阐述每个步骤，并通过示例说明如何在实际开发中应用这些方法。

### **（1）规范**

规范是从占位符推导来的，代表变化点是遵循一定规范的。通过定义规范，可以明确地表示哪些部分是可变的。

-   环境变量

环境变量代表在不同部署环境下会有所不同的配置项。例如，数据库连接字符串在开发、测试和生产环境下可能各不相同。

示例：在配置文件中定义环境变量，如DATABASE\_URL，在部署时根据环境设置不同的值

spring: datasource: url: ${DATABASE\_URL}

-   接口

接口定义了可以有一个或多个实现的规范，多个实现代表系统中的变化点。

示例：支付接口PaymentService，不同的支付方式（如信用卡支付、支付宝支付）实现同一个接口。

-   配置项

通过配置项可以选择不同的功能或实现。

示例：在配置文件中定义短信发送方式，通过配置选择使用阿里云或百度。

sms: provider: aliyun aliyun: access-key-id: 'xxxxx' access-key-secret: 'xxxxx' baidu: api-key: 'xxxxx'

-   注解

注解可以标识特定的行为或特性，通过注解来识别和处理变化点。

示例：使用@Transactional注解标识事务管理，框架会自动处理事务逻辑。

@Service public class OrderService { @Transactional public void placeOrder(Order order) { // 事务处理逻辑 } }

-   事件

通过同一事件的不同类型，触发相关的处理逻辑。

示例：定义用户注册事件，当用户注册事件发生，就可能触发其他相关处理逻辑。

### **（2）识别**

识别是找出系统中有哪些实现了规范的部分。通过识别，可以动态地发现和加载不同的实现。

-   接口实现识别

读取接口的实现类，通过反射或其他方式识别出所有实现。

示例：微信支付、支付宝支付都统一实现了支付接口PaymentService，通过接口就可以找到对应的所有实现类。

-   配置项变化监听

监听配置项的变化，当配置发生变化时，动态调整系统的行为。

示例：Spring Cloud Config或Nacos中可以监听配置变化，自动刷新配置。

-   注解扫描

扫描类路径下的注解，识别出哪些类或方法使用了特定注解。

示例：幂等组件自定义了注解@Idempotent，通过切面扫描到使用@Idempotent注解的类。

-   事件监听器

通过扫描和识别实现了事件监听接口的组件。

**示例**：识别所有实现了@EventListener注解的组件。

### **（3）注册**

识别出来的实现需要注册到系统中，以便在需要时可以方便地找到并使用。

-   Spring统一管理

Spring框架会自动管理所有Bean，将识别出的实现类注册到Spring上下文中。

示例：所有标注了@Component、@Service、@Repository的类都会被Spring管理，可以通过依赖注入的方式获取这些Bean。

-   类路径扫描

扫描类路径，识别出符合特定条件的类。

示例：Spring Boot会扫描META-INF/spring.factories文件，加载所有定义的自动配置类。

-   事件监听

通过事件驱动机制识别系统中的变化点。

例如，使用Spring Event机制监听和处理特定事件。

### **（4）使用**

使用就是找到具体实现并执行逻辑处理。通过前面步骤的规范、识别和注册，系统可以方便地找到所需的实现并使用。

总结：SPI 有它的规范，要到指定目录下加载对应文件；找到文件后进行解析、识别并加载；最后就是使用。整个流程能印证上面所提到的：规范、识别、注册、使用。所以，方法的提出有一个点就是从具体案例中进行抽象，提炼共性的东西，再去推演其它案例看能不能也满足。

# **二、可扩展性的实践**

我们把扩展性大致分为功能扩展和流量扩展。

**功能扩展**：旨在快速响应不断变化的功能需求，同时尽量减少对现有功能的影响。确保在添加新功能或修改现有功能时，系统能保持稳定并简化迭代成本。

**流量扩展**：为了应对用户量增长和数据增加，系统需要能够扩展其服务能力，处理不断增加的流量而不影响性能。确保系统能够在流量增加时保持高可用性和高性能。

## **2.1 功能需求变化的扩展性**

**功能扩展带来的挑战**

-   代码耦合度过高

功能的扩展往往需要修改大量的现有代码，导致系统的耦合度增加。高耦合度会使得功能的修改和维护变得更加困难。

-   缺乏灵活的扩展点

如果系统设计时没有预留足够的扩展点，新增功能时可能需要修改系统的核心部分，从而增加了开发和测试的成本。

-   复杂的依赖关系

当系统功能越来越复杂时，管理不同功能之间的依赖关系变得更加困难，可能导致系统难以维护和扩展。

### **2.1.1 架构设计应对**

#### **（1）模块化设计**

将系统分解为多个独立的模块，每个模块负责特定的功能。这种设计方式使得新增功能或修改现有功能变得更加容易。

**示例**：电商平台将支付功能独立为一个模块，方便添加新的支付方式。假设平台最初只支持信用卡支付，通过模块化设计，可以轻松集成新的支付方式，如支付宝和微信支付，只需在支付模块中进行扩展，而不影响其他功能。

#### **（2）微服务架构**

通过微服务架构，将系统拆分为一组小型、自治的服务。每个服务可以独立开发、部署和扩展，有助于快速响应业务需求的变化。

**示例**：将用户管理、订单处理、库存管理分别作为独立微服务，新增功能时只需更新相关微服务。例如，当需要新增会员系统时，只需添加一个新的微服务，而无需修改现有的用户管理和订单处理服务，这样可以快速响应业务需求的变化。

#### **（3）可插拔架构**

设计可插拔的组件，使得功能的添加或替换变得简便。这样，开发团队可以快速引入新功能或替换旧功能，而不需要大规模修改系统。

为系统设计插件机制，可以快速添加第三方功能。例如，系统支持第三方登录，通过可插拔架构，可以轻松集成微信、QQ、支付宝等多种第三方登录方式，而无需大规模修改系统。还有如可扩展性案例提到的各种组件，来降低耦合度。

#### **（4）识别扩展点**

确保系统在设计时能够识别和定义扩展点，以便于功能的新增和调整。这包括在设计阶段预留可配置的接口和扩展点。

通过代码审查和设计评审，确保所有潜在的扩展点都经过识别和定义。定期回顾和更新扩展点，以适应不断变化的需求。可以前瞻设计，但是要避免过度设计。

#### **（5）自定义 Starter**

当发现某些功能或配置在多个项目中重复出现，并且具有一定的复杂性和可封装性，那么自定义 Starter 会是一个很好的选择，能够提高开发效率、保证一致性和可维护性。

比如 Websocket Starter ，统一日志处理 Starter ，公司内部认证授权模块 Starter，短信发送 Starter 等。

这些案例展示了如何通过自定义 Spring Boot Starter 来封装特定功能，简化项目中的依赖管理和配置过程，提高代码的复用性和可维护性。实际应用中，可以根据具体的业务需求和场景来创建适合的 Starter。在实现自定义 Starter 时，关键是合理地组织依赖、配置类、自动配置逻辑，并通过spring.factories或新的自动配置方式让 Spring Boot 能够自动发现和应用这些配置。

自定义 Starter 在以下方面具有重要作用：

1\. 封装特定功能：可以将与特定业务或技术相关的复杂配置和依赖整合到一个自定义 Starter 中，方便在不同项目中重复使用，避免重复配置工作。

2\. 提供一致的开发体验：确保在多个项目中使用相同的功能时，配置和使用方式是一致的，减少因配置差异导致的问题。

3\. 隐藏复杂性：将底层的技术实现细节隐藏起来，使得开发者无需了解过多的技术细节，只需关注业务逻辑，即可轻松使用相关功能。

4\. 增强可维护性：将相关的配置和代码集中在一个地方进行管理和维护，便于进行版本控制和更新。

5\. 促进团队协作：团队成员可以共享和复用自定义 Starter，提高开发效率，减少沟通成本。

6\. 便于扩展和定制：可以根据项目的特定需求对自定义 Starter 进行灵活的扩展和定制，满足不同项目的个性化要求。

7\. 隔离业务逻辑：将特定的业务逻辑封装在自定义 Starter 中，与项目的其他部分隔离开来，使得系统架构更加清晰和模块化。

8\. 提升项目的可扩展性：为项目未来的功能扩展提供了便捷的途径，新的功能可以以新的自定义 Starter 或者对现有 Starter 的扩展的形式添加进来。

### **2.1.2 功能设计应对**

#### **（1）API优先**

通过API优先的设计方法，确保系统内部和外部的交互是通过标准化的接口进行的。这不仅提高了系统的互操作性，也使得功能扩展更加方便。

**示例**：通过标准化的RESTful API，让前端和后端团队可以并行开发和测试新功能。例如，电商平台的新用户注册功能，通过API优先设计，前端团队可以根据API文档独立开发用户注册页面，后端团队可以独立开发用户注册接口，两者可以并行工作，提高开发效率。

#### **（2）可配置性**

设计灵活的配置系统，使得功能开关和参数调整变得更加方便，能够快速适应业务需求的变化。通过使用配置文件、配置中心、动态配置、配置验证等方法，可以有效提高系统的可配置性。这不仅增加了系统的灵活性和维护性，也提高了在不同环境和需求下的适应能力。

**示例**：通过配置中心（如Spring Cloud Config），动态调整各微服务的参数和开关。例如，电商平台在促销活动期间，可以通过配置中心动态调整促销活动的开始和结束时间，而无需重新部署系统。这样可以快速响应业务需求的变化，提高系统的灵活性。

#### **（3）代码分层**

目前项目基本使用经典的三层架构，但是各层每个人的使用规范都不太一样，也是会导致代码质量慢慢不可控。

**规范问题及解决方案**

1\. **表示层与业务逻辑层耦合过高**

**问题**：表示层和业务逻辑层之间的耦合可能会导致业务逻辑代码与UI代码混合（如复杂校验、单位换算、格式转换、字段拼接等），使得维护和扩展变得困难。

**解决方案**：

-   使用视图模型（VO）：在表示层和业务逻辑层之间引入视图模型，将数据从业务逻辑层转换为表示层需要的格式。
-   保持单一职责原则：确保表示层只负责处理用户界面相关的任务，将业务逻辑放在业务逻辑层。

2\. **业务逻辑层逻辑复杂度过高**

**问题**：业务逻辑层中的逻辑可能会变得过于复杂，从而导致代码难以维护和测试。

**解决方案**：

-   分层处理业务逻辑：将业务逻辑拆分成多个服务或组件，每个服务或组件负责处理特定的业务逻辑。
-   定期进行代码重构：通过提取方法、合并重复代码和简化条件逻辑等方式，来降低业务逻辑的复杂度。

3\. **层间依赖管理不当**

**问题**：层间依赖不明确或不规范，可能导致层之间的依赖关系混乱。

**解决方案**：

-   明确依赖关系：遵循依赖倒转原则（DIP），确保上层（如业务逻辑层）不依赖于下层（如数据访问层）的具体实现，而是依赖于抽象。
-   依赖注入（DI）：使用依赖注入框架来管理和注入依赖，简化层之间的依赖管理。

4\. **错误处理不一致**

**问题**：不同层之间的错误处理机制不一致，可能导致错误难以跟踪和处理。

**解决方案**：

-   统一异常处理机制：在业务逻辑层和表示层中使用统一的异常处理机制，确保错误信息能够被正确地传递和处理。
-   自定义异常类：定义自定义异常类来处理特定的业务错误，并确保这些异常在不同层中能够得到一致的处理。

5\. **数据验证不充分**

**问题**：数据验证可能只在表示层进行，未能在业务逻辑层进行充分的验证，导致数据质量问题。

**解决方案**：

-   双重验证：在表示层和业务逻辑层都进行数据验证，确保数据的有效性和安全性。
-   使用验证框架：利用验证框架（如Hibernate Validator）来进行统一的数据验证。

通过关注这些规范问题和采取相应的解决方法，可以提升经典三层架构的可维护性、可扩展性和健壮性。

#### **（4）代码复用**

通过创建共享库（如工具类库、通用功能库），提升代码复用性，减少重复开发。

**示例**：例如，创建一个通用的HTTP客户端库，供各个服务调用外部API。

#### **（5）代码规范**

通过避免过大的类、过长的方法、过长的参数列、过多的条件判断、重复代码、无用代码、魔法值等，提供系统的整体扩展性，避免在发生某种变化时，需要在多个类做修改且容易造成其他逻辑问题。

1\. **避免过大的类**

-   单一职责原则（SRP）：确保每个类只有一个主要职责。如果一个类负责的功能太多，可以将其拆分为多个类，每个类处理一个单一的功能。
-   类的大小：定期审查和重构类的大小，避免一个类承担过多的功能。

2\. **避免过长的方法**

-   方法长度：保持方法简短，每个方法执行一个清晰的任务。一般建议每个方法的代码行数不超过 20-30 行。
-   方法拆分：如果方法过长，可以将其拆分为多个小方法，每个小方法执行一个独立的操作。

3\. **避免过长的参数列**

-   参数数量：尽量减少方法的参数数量。可以使用参数对象（将多个参数封装在一个类中）来简化方法签名。
-   可选参数：对于方法参数较多的情况，可以考虑使用构建者模式或可选参数来简化方法调用。

4\. **避免过多的条件判断**

-   策略模式：使用策略模式来处理复杂的条件逻辑，将不同的条件处理逻辑分开到不同的策略中。
-   多态：利用多态和继承减少条件判断，通过子类实现不同的行为。

5\. **避免重复代码**

-   DRY原则（Don’t Repeat Yourself）：避免在代码中重复实现相同的功能。将重复代码提取到公共方法或类中，复用现有的功能。
-   工具类：将常用的操作封装到工具类中，以减少代码重复。

6\. **避免无用代码**

-   代码审查：定期进行代码审查，删除未使用或冗余的代码。
-   清理：使用静态分析工具来检测和删除无用代码。

7\. **避免魔法值**

-   常量定义：将“魔法值”定义为常量，并给常量命名，以提高代码的可读性和可维护性。
-   配置文件：将需要经常修改的值放在配置文件中，避免硬编码在代码中。

#### **（6）版本控制与向后兼容**

在API和数据库设计中，确保向后兼容。

**示例**：新增API时，保留旧版本的API接口，保证旧版客户端仍能正常使用；数据库中新增字段或表时，避免对现有数据结构的破坏，通过版本控制和数据迁移脚本，确保系统平稳过渡。

#### **（7）持续集成和持续部署**

实施CI/CD流程，使得新功能的开发、测试和部署变得高效和可靠，能够快速将新功能交付给用户。

**示例**：使用Jenkins自动化构建和部署新功能，减少上线时间和风险。例如，开发团队完成新功能后，提交代码到Git或SVN仓库，Jenkins自动拉取代码进行构建、测试和部署。通过自动化流程，可以快速将新功能交付给用户，同时确保每次部署都是稳定可靠的。

#### **（8）设计模式的应用**

设计模式本质上乃是对面向对象设计原则的切实运用，其实质是大佬们在代码设计方面经验的凝练总结，是用于解决特定问题的一连串套路。

以下是一些设计模式在 Spring Boot 中的常见应用：

-   单例模式：Spring 管理的 Bean 默认是单例的，比如配置类、服务类等。这样可以保证在整个应用中只有一个实例存在，节省资源并提高性能。
-   工厂模式：Spring 的 @Bean 注解方法可以看作是一种工厂方法。通过配置不同的方法，能够根据条件创建不同的对象实例。
-   代理模式：Spring AOP（面向切面编程）基于动态代理实现。例如，在进行事务管理、日志记录、权限控制等方面，通过创建代理对象在方法执行前后添加额外的逻辑。
-   观察者模式：Spring 的事件机制采用了观察者模式。可以自定义事件，并在相关操作发生时发布事件，其他组件通过注册监听器来响应事件。
-   模板方法模式：在 Spring 的 JdbcTemplate 类中有所体现。它定义了数据库操作的基本流程，而具体的 SQL 语句和数据处理在子类中实现。
-   策略模式：例如在 Spring 的条件注解（如 @ConditionalOnProperty ）中，根据不同的条件选择不同的配置或组件加载策略。
-   责任链模式：在 Spring Security 中，多个过滤器组成的认证和授权链可以看作是责任链模式的应用。
-   装饰器模式：在 Spring 中对某些功能的增强可以通过自定义 HandlerInterceptor 来实现，这类似于装饰器模式。

这些设计模式的应用使得 Spring Boot 框架具有高度的灵活性、可扩展性和可维护性，能够更好地应对复杂的业务需求和变化。

## **2.2 流量数据变化的扩展性**

在面对流量突增时，系统需要具备有效的扩展性以维持正常服务。流量激增可能导致应用服务器过载，影响其他服务的性能。

**流量数据变化带来的挑战**

-   应用服务器过载

流量激增可能导致应用服务器无法处理大量请求，进而影响系统的可用性。

-   服务间牵连效应

一个服务的流量激增可能影响到其他服务，导致整体系统变慢或无法响应。

-   数据存储瓶颈

数据库可能成为瓶颈，特别是在高并发读写操作时，影响整体性能。

### **2.2.1 架构设计应对**

#### **（1）自动化扩展**

通过自动化扩展机制，在流量增加时自动增加服务器资源，在流量减少时释放多余资源。

**示例**：战训平台在大型考试任务期间，使用自动化扩展在流量高峰时增加实例数量，保障系统稳定。在流量高峰时，自动增加实例数量，确保系统能够处理激增的请求量；在流量回落时，自动减少实例数量，节省成本。

#### **（2）负载均衡**

使用负载均衡器（如Nginx）将流量分配到多个服务器，确保每个服务器都能均衡地处理请求，避免单点瓶颈。

**示例**：使用Nginx负载均衡，将用户请求分配到多台后端服务器，防止单一服务器过载。

#### **（3）微服务架构**

将系统拆分为多个独立的服务，每个服务可以独立扩展，确保某个服务的流量激增不会影响其他服务的正常运行。

**示例**：拆分战训平台为用户服务、训练服务和考试服务，当大型考试任务期间考试量激增时，可以单独扩展考试服务，也可以针对性的扩展高流量的训练服务，而其他服务保持原样。

#### **（4）数据库分片**

通过数据库分片（Sharding）和复制（Replication）来提升数据库的读写性能。

**示例**：将数据库按照用户ID进行分片，不同分片的请求由不同的数据库实例处理，提升整体性能。例如，将用户数据分成3个分片，分别存储在3个数据库实例中。用户请求根据用户ID分配到对应的数据库实例，避免单一数据库实例成为瓶颈。同时，使用主从复制提高读性能，主库处理写请求，从库处理读请求，进一步提升数据库性能。

### **2.2.2 功能设计应对**

尽管功能设计应对流量和数据变化通常涉及性能优化，但它仍然与系统的可扩展性紧密相关。合理的设计不仅能帮助系统应对当前的负载，还能为未来的流量和数据增长做好准备。

#### **（1）缓存策略**

采用合适的缓存策略，通过分布式缓存（如Redis、Memcached）减少对数据库的直接访问，提升系统的响应速度和承载能力。

示例：在用户频繁查询的设备信息上使用Redis缓存，减少数据库查询次数。

#### **（2）异步处理**

对于非实时性任务，采用异步处理方式，通过消息队列（如Kafka、RabbitMQ）来解耦系统组件，平滑处理高并发请求。

示例：用户操作后，接口请求和日志记录的操作异步进行，提升响应速度。（对于重要的操作，需要失败重试或记录手动处理）

#### **（3）无状态服务**

设计无状态服务，使得请求可以被任何一个节点处理，方便进行负载均衡和水平扩展。

**示例**：通过设计无状态的API服务，使请求可以分配到任意服务器处理。

**反例**：API服务存在本地缓存、本地磁盘、本地定时任务，会造成数据不一致或重复执行的问题。

#### **（4）限流和熔断**

通过限流和熔断机制保护系统不被突发流量压垮，确保在高负载下系统依然能够提供核心服务。

**示例**：在API网关上实施限流策略，如每秒最多允许某用户访问特定API 10次，超出部分直接返回错误。这可以防止某些恶意用户发送过多请求影响系统性能（互联网环境下很容易被恶意刷接口）。同时，在服务中实现熔断机制，当某个依赖服务响应时间过长或不可用时，快速返回预设的降级响应，避免整个系统被拖垮。

# **三、总结**

扩展性是系统设计中的重要组成部分，它直接影响到系统的稳定性和性能。在系统建设初期，优先考虑扩展性可以为后续的发展和扩展打下坚实的基础。希望通过今天的分享，大家能够对扩展性有更深的理解，并在实际工作中应用这些方法，使我们的系统能够在不断变化的环境中保持强大、稳定和高效。
