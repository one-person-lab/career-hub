# 系统稳定性

目标：学习提高系统稳定性的策略，有助于确保系统稳定运行

这个系列涵盖三个核心方面：**扩展性、性能和稳定性**。

-   扩展性：让系统更加**灵活和强大**。
-   性能：让系统运行更加**高效**。
-   稳定性（也称**可靠性**或**高可用**）：确保系统能够**持续稳定地运行**，即使在高负载或突发情况下也能保障业务连续性。

今天我们将重点探讨**稳定性**，深入理解如何设计**高可用系统**，提高系统**故障应对能力**。

# **一、稳定性的介绍**

## **1.1 稳定性的重要性**

**（1）用户体验与满意度**

-   系统可用性直接影响用户信任与品牌形象。
-   避免频繁宕机，减少用户流失，提高用户黏性。

**（2）业务连续性与损失控制**

-   系统崩溃会导致交易中断、脏数据产生。
-   业务系统如果不可用，可能带来直接经济损失。

**（3）减少运维与开发成本**

-   稳定性高意味着更少的**故障排查和系统重构**，减少额外运维投入。
-   提高稳定性可以减少团队疲劳，降低紧急事件响应频率。

## **1.2** **稳定性****的衡量指标**

-   系统可用性 (Availability)

-   公式：可用性 = 正常运行时间 / (正常运行时间 + 停机时间)

-   **【MTTF】**是指平均正常时间（Mean Time To Failure）。示例：系统平均每60分钟挂一次，MTTF=60分钟。
-   **【MTTR】**是平均修复时间（Mean Time To Repair），示例：每次修复耗时10分钟，MTTR=10分钟。

-   常用衡量标准：99.9%（三个九）、99.99%（四个九）等。

**提高可用性措施：**

降低MTTR：减少故障数量，提升发现速度，提升恢复速度。

\[未知卡片\]

-   错误率 (Error Rate)

-   衡量**请求失败**的比例，例如API调用失败率、网络包丢失率。

-   故障影响范围

-   判断故障波及范围，是影响**全局**模块还是仅**局部**服务。

## **1.3** **稳定性****影响因素**

\[未知卡片\]

系统的**变化性和不可控性**决定了任何事物都不可能**100%可靠**，这就要求我们识别不同层面的风险并制定应对措施。

### **1.3.1 变更类风险**

-   代码变更

-   回归测试不足、未覆盖所有场景。

-   配置变更

-   配置更新未及时同步，导致环境不一致。

-   数据变更

-   缓存格式变更导致缓存不一致。

-   系统重启

### **1.3.2 流量类风险**

-   上游请求突增
-   网络流量风险

-   **流量激增**导致网络拥塞，影响所有网络请求的响应时间。

-   API请求过载
-   热点KEY问题

-   大促或热门活动期间，某些数据（如**缓存KEY**）被频繁访问，导致单机节点资源耗尽。

### **1.3.3 依赖类风险**

-   **下游响应慢或错误**

### **1.3.4 固件类风险**

-   计算资源问题

-   服务器资源（CPU、内存、IO）不足会导致系统性能下降，甚至引发崩溃。
-   应用资源（RPC线程数，DB连接数等）耗尽，导致服务不可用。

-   存储资源问题

-   磁盘满、单表容量超限等问题会导致数据读写错误。
-   数据库**主从同步延迟**可能导致查询到过期数据。

-   硬件故障

-   硬件损坏（如服务器宕机、磁盘损坏），或网络中断会导致服务中断。
-   必须定期维护和监控服务器硬件状态，确保其可用性。

### **1.3.5 安全类风险**

-   恶意攻击

-   DDoS攻击可能导致系统资源耗尽、服务不可用。

### **1.3.6 时间类****风险**

-   时间变化：时间到期

# **二、稳定性保障手段**

## **2.1 架构设计**

### **2.1.1 消除单点故障**

-   水平扩展（Scale-Out）：通过集群和副本减少单一节点宕机风险。
-   主备切换：主服务发生故障时自动切换到备用服务（如数据库主从同步）。

-   **应用场景**：数据库主从切换（如MySQL、PostgreSQL），消息队列的高可用（如RabbitMQ、Kafka）。

-   **负载均衡：**使用Nginx、LVS等分配流量，避免单机超载。

-   结合健康检查实现自动剔除故障节点。

-   熔断机制（Circuit Breaker）

-   当下游服务出现异常或响应变慢时，快速熔断以保护系统，避免请求持续占用资源。

### **2.1.3 代码设计优化**

-   数据一致性
-   模块化与解耦设计

-   将系统拆分为多个独立服务，减少模块之间的强依赖，避免单点故障影响全局。

-   **预热与削峰填谷**

-   预热：缓存关键数据，避免流量高峰时性能下降。

-   日志打印

## **2.2 安全设计**

-   防SQL注入攻击

-   使用参数化查询、ORM框架避免SQL注入。

-   身份认证与权限管理

-   强化 **RBAC**（基于角色的访问控制），避免越权访问。

-   数据备份与恢复

-   定期备份数据并测试恢复机制，避免数据丢失或被攻击。

-   资源消耗频次管控

-   控制资源消耗频次，如短信发送频率限制，避免滥用。

-   敏感信息脱敏

-   对用户数据（如手机号、身份证号）进行脱敏处理，防止敏感信息泄露。

## **2.3 变更规范**

### **2.3.1 可监测**

-   智能告警：

-   针对API响应时间、数据库连接数、内存占用等设置阈值，并通过短信、邮件等发送告警。

-   日志分析

-   通过日志系统（如 ELK）进行异常分析，实现问题的快速定位和根因排查。

-   实时监控与指标采集

-   **Prometheus + Grafana** 监控CPU、内存、连接池等系统指标，并提供可视化面板。

### **2.3.2 可灰度**

-   灰度发布
-   蓝绿发布

-   同时运行两个版本系统（蓝、绿环境），用户请求逐步切换到新版本，若出现问题可快速回滚。

-   金丝雀发布（Canary Release）

-   将新功能只开放给极少部分用户，用于检测系统是否稳定。

### **2.3.3 可回滚**

在新版本出现故障时，系统支持无缝回退到上一个稳定版本。

-   配置回滚

-   每次变更前备份配置，必要时切换至上一个稳定版本。

-   数据库回滚

-   备份表结构和数据，变更失败时执行数据恢复。

-   代码回滚

-   Git代码管理配合**CI/CD**工具（如Jenkins），一键回退到上个版本。

### **2.3.4 测试标准**

-   多环境测试

-   在开发、测试、预发布、生产环境中逐步验证变更。

-   性能测试

-   使用JMeter等工具进行压力测试，提前发现系统瓶颈。

-   回归测试

-   保障变更不会影响其他模块功能，避免引发新问题。

## **2.4 故障恢复**

### **2.4.1 回滚**

在故障发生后快速恢复系统至上一个稳定状态，避免问题扩大。

-   自动化回滚

-   利用 CI/CD 工具（如 Jenkins）实现一键回滚。
-   结合 Git 分支管理，确保每次发布有版本快照作为备份。

-   数据库回滚

-   使用增量备份快速恢复数据库状态。

-   配置回滚

-   利用配置中心（如Nacos）自动切换至上个稳定版本。

### **2.4.2** **重启**

在部分服务或组件出现异常时，通过重启快速恢复运行状态。

-   定向重启

-   仅重启异常模块，避免影响全局服务。

-   平滑重启
-   重启风控策略

-   限制短时间内重启次数，避免频繁重启引发雪崩效应。

### **2.4.3** **限流**

当系统负载达到上限时，通过限流避免系统崩溃并逐步恢复。

-   静态限流

-   使用固定限额对流量进行控制，如最大 QPS 限制。

-   动态限流

-   基于系统实时负载调整限流策略。

-   熔断与降级结合

-   当服务响应时间超标时，自动限流并熔断部分请求。

### **2.4.4** **降级**

在系统资源不足时暂停非核心功能，确保关键业务正常运行。

-   服务级别降级

-   临时停用非关键模块（如推荐系统），保障核心业务（如支付流程）稳定。

-   功能降级

-   高并发场景下简化业务逻辑，如将复杂查询替换为缓存数据。

-   页面降级

-   当请求量超出服务器承载能力时，展示简化页面（如静态页面）。

-   自动化策略

-   使用 Sentinel 等工具自动触发降级策略，防止服务全面崩溃。

### **2.4.5** **扩容**

通过增加资源应对高并发和瞬时流量峰值，确保系统稳定运行。

-   水平扩展

-   增加服务器节点，通过负载均衡器（如 Nginx）将流量分摊到多个实例。

-   垂直扩展

-   临时提升服务器的 CPU、内存等资源。适用于虚拟化环境或云端资源。

-   自动扩容

-   使用 K8s 的 **HPA（Horizontal Pod Autoscaler）** 实现动态扩容。
-   基于业务高峰时段的预估，提前扩展资源。

### **2.4.6 自愈机制**

通过自动检测与恢复手段，实现系统自我修复，减少人工干预。

-   自动重启与重试

-   在检测到异常后自动重启服务。

-   健康检查与剔除故障节点

-   结合 **Consul** 或 **Nacos** 检测服务状态，并自动剔除故障节点。

# **三、稳定性排查手册**

## **3.1 常见问题**

1.  逻辑缺陷
2.  性能瓶颈
3.  内存异常

### **3.2.1 快速止血**

快速止血的目的是及时控制问题，避免进一步扩散。

1.  发布后立即报错

4.  单用户流量激增
5.  下游服务故障

### **3.2.2** **保留现场**

**止血后，尽量保留现场**以供后续分析。

1.  隔离问题机器
2.  Dump 快照
3.  日志与监控回溯

### **3.2.3** **定位原因**

问题根因往往隐藏得较深，需要综合多种手段排查。以下是一些常见分析方法：

1.  变更排查
2.  全链路追踪分析
3.  时间线还原
4.  深入挖掘根因
5.  问题复现

### **3.2.4** **解决问题**

定位到问题根因后，需要妥善处理和发布解决方案。以下是几个重要步骤：

1.  变更测试与灰度发布
2.  线上验证与观察
3.  故障复盘与知识库积累
