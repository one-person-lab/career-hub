# ElasticSearch

# 基础

Elasticsearch(ES)是一种基于分布式存储的搜索和分析引擎。

## 节点（Node）

节点就是单个的Elasticsearch实例，该实例运行的载体可以是物理服务器或虚拟机器。

## 集群（Cluster）

集群是节点的集合。

集群是一组运行在不同载体（物理或虚拟机器）上的一个或多个Elasticsearch节点的集合。在集群内，节点间相互合作，对数据进行存储和管理。

## 分片（Shards）

分片是索引的片段。

受制于单个ES节点的性能上限（内存、磁盘IO速度），如果数据以整块形式进行存储与管理，则无法足够快速地响应客户端的请求，因此ES将索引拆分为更小块的分片，以便分布式存储和并行处理数据。

## 副本（Replicas）

副本是分片的拷贝。

每个分片可以有零个或者多个副本，副本与分片对外都可以提供数据查询服务。副本的存在可以增加整个ES系统的高可用性，高并发性，因为分片能做到的事情，副本也能做到。计算机世界里没有银弹，副本的开销主要体现在数据同步成本的增加（每次数据更新时，都需要把分片上的数据变更同步到其他副本中）。

## 文档（Document）

索引中的每一条数据叫作一个文档，它是一个JSON格式的数据对象。对应关系型数据库中的数据行。这一点与非关系型数据库MongoDB很类似，MongoDB属于文档数据库，每条数据也是一个BSON文档（BinaryJSON）。非关系型数据库的文档相比关系型数据库的数据行，优势在于提供了更高的自由度，文档中可以方便地新增减字段，多个文档间也不要求字段完全一致。同时，文档也保留了一部分结构化存储的特性，对存储的数据进行了一定的结构化封装，而没有像K-V非关系型数据库那样完全抛弃数据的结构化。

## ES套件Logstash

是ES官方套件系列中的数据同步工具。支持在config配置文件中写入需要的SQL逻辑并存储为视图，并通过视图来写入多表查询的结果到ES。这种方式自由度较高，能够方便地构建所需要的数据。但是数据同步的性能略差（秒级别）。

# 常见问题

## ES深度分页如何优化？

深度分页的性能问题是 ES 中的常见难题，关键在于**规避无意义的资源消耗**：

-   优先选择 search\_after 和 scroll 游标查询。
-   限制分页深度或改变分页需求。
-   对索引、字段映射和查询方式进行优化。

游标查询

-   滚动时间：scroll 参数指定的时间是每次查询保持游标有效的时间（例如1分钟）。如果在游标有效期内没有发起新的请求，游标会超时并被销毁。
-   性能：使用 scroll 查询的性能较好，尤其是需要遍历大量数据时，因为 ES 会维护一个快照，避免了重复计算和排序。但需要注意的是，scroll 查询的数据不实时更新，如果数据发生了变化，可能会错过新增的数据或重复返回已删除的数据。
-   批量处理：对于大量数据的查询，建议每次返回一个合理数量的数据（例如100或1000），避免一次性返回过多数据导致内存溢出。

## ES性能优化

-   索引优化
-   使用合适的数据类型，避免存储大量不必要的文本数据

**合理使用过滤器**

-   避免频繁的正则表达式查询：正则表达式查询效率低，尽量避免使用。
-   使用 **keyword 字段进行过滤**：对于需要过滤的字段，应使用 keyword 类型而不是 text，这样查询效率更高。

ElasticSearch 性能优化是一个系统性工程，从硬件、索引设计、查询优化、集群管理等多个层面入手。关键措施包括合理配置硬件资源、精心设计索引和字段映射、优化查询DSL和聚合策略、合理配置副本和分片、采用批量写入和延迟刷新策略等。

在实际生产环境中，应根据业务需求和数据量的增长情况定期进行性能调优和监控，确保 ElasticSearch 集群始终保持高效稳定运行。

## 如何优化 ElasticSearch 的地理位置查询性能？

-   合适的字段类型：对于地理位置数据，使用 geo\_point 类型而不是 text 或 keyword，这能有效提高查询性能。
-   优化查询范围：尽量使用精确的地理查询（如 geo\_distance 查询），避免不必要的复杂查询。
-   缩小查询范围：尽量减少需要查询的地理范围，避免全地球范围的查询。
-   使用 Geo Hash：如果地理位置查询的精度要求不高，可以使用 geo\_hash 来加速查询。geo\_hash 是对地理位置的一种空间索引方式，能显著提升查询性能。
-   索引设计：如果数据量非常大，可以考虑对经常查询的区域创建地理位置聚类索引（例如，以特定网格划分区域），以便更高效地进行查询。

## **什么是倒排索引？ES 如何使用它？**

倒排索引是全文检索系统的核心数据结构，用于快速查找包含某些词条的文档。它由词典和倒排列表组成，词典存储所有的词条，倒排列表记录词条所在的文档 ID 列表以及可能的额外信息（如词频、位置等）。

在 Elasticsearch 中，当我们对文档字段进行索引时，系统会通过分词器将字段内容拆解为词条，并构建倒排索引。这种结构支持快速的关键词搜索、布尔查询等多种操作。举个例子，假如我们搜索‘fast retrieval’，Elasticsearch 会找到‘fast’和‘retrieval’对应的倒排列表，然后通过交集计算获取包含这些词的文档。

#### **1\. 索引过程**

在文档被写入 ElasticSearch 后：

1.  分词：文档内容被分解成独立的单词（Token）。
2.  建立倒排索引：根据分词结果，构建单词与文档 ID 的映射关系，并存储在倒排索引中。

你如何设计一个日志检索系统？

-   数据采集：使用 Logstash、Filebeat 或 Fluentd 收集日志并推送到 ElasticSearch。
-   数据存储：日志根据时间创建索引（如每日一索引）。
-   查询优化：

-   配置适合的分片数和副本数。
-   使用过滤器而非全文查询进行时间范围过滤。

-   展示层：通过 Kibana 构建数据仪表盘或提供搜索界面。

ElasticSearch 中的 Query 和 Filter 有何区别？

-   Query：用于全文检索，支持相关性评分。适合不需要精确匹配的场景。
-   Filter：用于精确匹配或布尔逻辑，结果不参与评分，效率更高。

-   典型用例：范围查询、标识符匹配。

如果某个索引查询性能较差，你会如何优化？

-   索引优化：

-   确保字段使用合适的映射类型（如 keyword vs text）。
-   避免创建过多的字段。

-   分片调整：

-   减少分片数（过多分片会导致管理开销）。
-   副本调整以提升查询性能。

-   缓存利用：

-   使用 **filter cache** 提高重复查询的效率。

-   查询优化：

-   使用过滤器替代全文检索查询。
-   仅返回所需字段（\_source 控制）。

-   硬件资源：

-   增加节点数，升级硬件（如 SSD）。

如果一个查询非常慢，你如何排查问题？

-   Profile API：分析查询的执行计划，找出瓶颈。
-   Explain API：查看查询如何被分解和执行。
-   慢查询日志：启用慢查询日志，定位具体问题。
-   节点监控：检查集群健康、节点负载（CPU、内存、磁盘 I/O）。
-   映射问题：确保字段映射正确，避免使用 text 类型处理精确匹配需求。

你对 ElasticSearch 聚合的理解？

聚合是一种数据分析功能，可以将文档数据进行分组、统计和计算。主要类型有：

-   Bucket 聚合：按字段分组（如 terms、range）。
-   Metrics 聚合：计算值（如 sum、avg、max）。
-   Pipeline 聚合：对已有聚合结果再处理（如 moving\_avg）。

**问题：**

-   在实现疫情人员聚集的时空伴随功能时，你如何设计 Elasticsearch 中的数据模型？如何定义字段和映射类型来存储和查询时空数据？
-   如何确保大规模数据集在 Elasticsearch 中的高效存储和检索？你是否进行了索引优化（如分片、刷新频率等）？

**回答思路：**

-   数据模型设计时，要使用合适的字段类型。例如，使用 geo\_point 类型来存储人员的地理位置信息，使用 date 类型来存储时间戳。
-   对于大规模数据集，应该优化 Elasticsearch 索引策略，包括合理选择分片数量、主副本配置，以及通过适当的 refresh 间隔来优化写入性能。
-   如果涉及时间序列数据，可以考虑基于日期范围或事件划分索引，以提高查询效率。

**问题：**

-   在构建时空伴随查询时，如何处理空间（地理位置）和时间两个维度的数据？你是如何进行地理位置查询的？
-   你是如何设计查询来检测疫情人员的聚集区域及其时空变化的？

**回答思路：**

-   使用 **Geo Distance Query** 或 **Geo Polygon Query** 来进行空间范围查询，同时结合 **Range Query** 来处理时间维度。例如，可以查询特定时间范围内在某个地理区域内的人员聚集情况。
-   时空伴随的查询可以通过聚合（比如基于时间的直方图聚合）来查看疫情趋势，并使用 geo\_distance 或 geo\_tile 聚合进行空间分析。

主要的非关系模型有KV模型、宽表模型、文档模型、图模型、时序模型等：

-   KV模型：主要特征是将每个数据值与唯一的键关联起来，适用于OLTP场景，例如 Amazon's DynamoDB；
-   宽表模型：主要特征在于动态列、多版本、TTL，其自动分裂的特性和基于lsm-tree的存储引擎提供了强大的水平伸缩性和写入吞吐量，特别适用于稀疏数据集的海量写入和查询场景。业界主流产品是 BigTable 和 HBase，HBase 是 BigTable 的开源实现；
-   文档模型：主要特征在于提供了最接近于真实的业务对象模型的 JSON/BSON 存储格式，是一种对开发非常友好的存储模型。业界主流产品是 MongoDB，其与 Express、Angular、Node.js 等开源技术栈一起构成了 MEAN Stack；
-   图模型：主要特征在于提供了点和边的存储语义，可以高效执行跨节点和边的网络查询，易于描述实体间的关系。业界主流产品是 Neo4J；
-   时序模型：主要特征在于提供了时间序列数据的建模能力，将时序数据抽象为指标、标签、时间戳三个维度。业界主流产品是 InfluxDB、Prometheus、OpenTSDB 等，InfluxDB 与 Telegraf、Chronograf、Kapacitor 等组件一起组合为 TICK Stack；
