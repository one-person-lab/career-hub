# Redis

# Redis的调优实战经历？

## 问题背景

-   数据存储在Redis的ZSet结构，出现积分清空的问题。
-   原因是分片内存达到上限，触发了LRU策略，删除了带有过期时间的key。

## 问题排查过程

-   确认集群容量：从16G扩容至32G，发现单个分片（4G）满了。
-   CLUSTER KEYSLOT 定位问题key的分片，导出并分析内存。
-   发现大key：一个key占用2.5G，堵塞分片。
-   解决方法：释放空间，并规范缓存设计。

## 教训与优化

-   规范过期时间：避免列表结构数据持续增长，导致大key问题。
-   分散key设计：大数据量场景拆分到多个key，分布在不同分片。
-   监控分片：设置内存报警和关键key监控，避免触发删除策略。

线上跑修数脚本，对测试用户的班级排行榜进行修数时，发现班级排行榜的所有学生积分被清空

而且发现学生积分有变动时，调用redis的zincryby操作与expire操作时，key都会被清空，学生的积分无法添加

这时候就通过rdbtools进行内存分析，发现有个key占用了2个多G的内存，存在大key，后来释放了空间，才解决问题

这个也属于历史遗留的问题，一直都没发现，以前很多key没有设置过期时间，并且不断往集合里新增，导致出现大key

通过此次的排查调优，也规范了Redis的使用

使用zset、set、list、hash之类的列表结构，业务不断往里面新增内容，又不设置过期时间，会导致key不断增大，堵塞集群分片、触发删除策略一系列问题，如果有存在大key的可能，应该要分散到多个key上，从而把数据分散到集群的不同分片上，并且应该设置过期时间

# Redis的持久化方案？

> RDB + AOF: 生产环境推荐组合使用。

## RDB（redis database backup）快照

-   定时将内存数据保存到磁盘。
-   优点：性能高效，适合冷备份。
-   缺点：可能会丢失最近修改的数据。

在指定的时间间隔，将内存数据写入磁盘，默认文件名为dump.rdb。同步方式为save命令（会阻塞所有操作），异步方式为bgsave命令（执行fork操作创建子进程会阻塞），全量备份，适用于备份和灾难恢复，可能存在数据丢失，自动触发save m n，m秒内存在n次修改则触发bgsave。

开启方式：

save 900 1

## AOF（append only file）追加日志

-   记录每次写操作，追加到日志文件。
-   优点：数据安全，丢失数据少。
-   缺点：文件体积较大，写性能稍逊。

将每一次收到的命令追加到文件中，当存在误删的情况，很容易紧急恢复。体积较大，恢复较慢。可以使用AOF文件重写，减少磁盘占有量，加快恢复速度，但是影响性能不推荐使用。

开启方式：

appendonly yes

appendfsync always

嗯，Redis主要有两种持久化方式AOF和RDB，AOF是将每一次执行的命令写到日志文件中，更加可靠，但也更加耗费磁盘空间，如果更加注重数据安全，选用这个。RDB是将内存数据写入磁盘，在满足一定的条件后会自动触发全量备份，当Redis实例故障重启后，从磁盘读取快照文件，恢复数据。

# **Redis 是什么？**

Redis 是一个高性能的开源 NoSQL 数据库，基于内存存储，支持持久化。

主要特点：

-   支持多种数据结构（字符串、哈希、列表、集合、有序集合等）。
-   高性能，读写操作速度非常快（百万 QPS）。
-   支持持久化（RDB 和 AOF）。
-   提供丰富的功能（发布/订阅、事务、Lua 脚本）。
-   支持主从复制和哨兵机制，实现高可用。
-   提供 Cluster 模式，支持分布式部署。

# **Redis 的性能优化？**

-   合理使用数据结构: 根据场景选择适合的数据结构。
-   控制键值大小: 避免存储大对象，推荐拆分或分片。
-   设置过期时间: 自动清理无效数据。
-   使用管道（Pipeline）: 减少网络延迟。
-   缓存雪崩/穿透/击穿:

-   雪崩: 设置不同过期时间，使用多级缓存。
-   穿透: 使用布隆过滤器。
-   击穿: 使用锁或加载保护机制。

-   使用主从复制分担读写压力。
-   开启 Lazy Free: 延迟删除大对象。

# **Redis缓存雪崩、缓存穿透、缓存击穿怎么解决？**

嗯，缓存雪崩其实就是在某个时间段内，缓存中的大量数据同时失效或过期，导致大量的数据直接访问数据库。通常以预防为主，之前的项目中就有遇到过使用Redis设置的过期时间是一致的，这就存在雪崩的可能，当时就对过期时间设置了一个随机的偏移量，确保缓存不会同时失效。对一些热点数据设置了缓存预热，并且使用集群部署。

嗯，缓存穿透是指当请求一个不存在缓存中的数据时，导致大量的请求直接访问数据库，可能引发数据库压力过大。缓存穿透通常是由于恶意请求引起的。可以通过空值缓存或者使用布隆过滤器，但是空值缓存会造成内存消耗，并且可能出现数据不一致的情况。如果真的发生了缓存穿透，这时候可以采用降级或限流。

嗯，缓存击穿是刚好热点的key设置了过期时间，且刚好过期，恰好这个时间点对这个key有大量的并发请求，这时候可能把数据库压垮。使用互斥锁，但是性能会比较低。对于一些非常热门的数据，可以设置成永不过期，或者最近最少使用过期策略，确保这些数据始终在缓存中。如果数据库的负载仍然过高，可以采取降级策略，返回默认数据或错误信息，以保证系统的稳定性，也可以部署集群来保证高可用性。

**哨兵选主的规则**

当有多个从节点符合条件时，按以下优先级选主：

1.  优先级（priority）: 每个从节点有一个 slave-priority 值，优先选择优先级数值最低的节点。

3.  从节点 ID: 如果复制偏移量相同，则选择 ID 最小的从节点（一个简单的唯一标识符）。

## **3\. 分片集群**

**原理**

-   Redis Cluster 是一种分布式架构，将数据分片存储在多个节点中，提供高可用和高扩展性。通过分片存储和多主多从结构，支持大规模数据和高并发场景，同时自动故障转移和客户端重定向机制保证了高可用。
-   特点:

-   无中心结构，每个节点存储自己的数据和集群元数据。
-   使用哈希槽（Hash Slot）分片，共 16384 个槽。
-   节点通过 Gossip 协议通信，定期交换集群状态信息。

分片集群特征，集群中有多个master，每个master保存不同数据，每个master都可以有多个slave节点，master之间通过ping检测彼此健康状态，客户端请求可以访问集群任意节点，最终都会被转发到正确节点上。

Redis会把每一个master节点映射到0~16383共16384个插槽上，数据key不是与节点绑定，而是与插槽绑定，redis会根据key的有效部分计算插槽值，利用CRC16算法得到一个hash值，然后对16384取余，得到的结果就是slot值。为什么不与节点绑定，因为节点是可能宕机或者伸缩的。集群宕机或者扩容，插槽可以跟着转移。

**迁移示例**

假设初始集群有两个节点 A 和 B：

-   A 负责槽 0～8191
-   B 负责槽 8192～16383

新增节点 C 后，重新分配槽：

1.  将槽 6000～8191 从节点 A 迁移到节点 C。
2.  将槽 12000～16383 从节点 B 迁移到节点 C。

迁移完成后：

-   A：0～5999
-   B：8200～11999
-   C：6000～8191 和 12000～16383

如何将同一类数据固定的保存在同一个Redis实例？这一类数据使用相同的有效部分，例如key都以{userId}为前缀。所有键 {userId} 相关的数据都会映射到同一个哈希槽上。

#### **高可用机制**

-   每个主节点有 1~n 个从节点，用于容灾备份。
-   如果某个主节点宕机，其从节点会被自动提升为主节点。
-   客户端重定向机制：当请求的数据槽不在当前节点时，返回 MOVED 或 ASK，引导客户端请求正确节点。

#### **优缺点**

-   优点:

-   提供分片存储，支持水平扩展。
-   主从架构保证节点高可用。
-   自动故障转移。

-   缺点:

-   部署和运维复杂。
-   数据访问需要增加槽分片逻辑。

#### **生产建议**

-   每个分片至少配置 1 个从节点，保证容灾能力。
-   使用合理的分片策略，避免数据倾斜。
-   定期检查和维护节点状态，防止分裂脑（Split-Brain）。

# **Redis主从数据同步的流程是什么？**

主从全量同步

从节点执行replicaof命令，请求数据同步，主节点判断是否第一次同步，是第一次就与从节点同步版本信息，主节点执行bgsave，生成rdb文件发送给从节点执行，在rdb生成和执行期间，缓存新写的命令，再发送给从节点进行同步。

主从增量同步

从节点请求主节点同步数据，节点判断不是第一次同步请求，就获取从节点offset值，主节点从命令日志获取offset值之后的数据，发送给从节点进行同步。

缺点：主从复制不能保证高可用，一旦主节点宕机，需要人工干预。

\# ip port 是 master的，配置完成主从节点之间的数据同步会自动进行，不需要人为插手 replicaof ip port

# **ZSet的底层实现原理？**

Redis 的 ZSet 底层实现使用了 **跳表**（SkipList）和 **哈希表**（HashMap）的结合。跳表负责有序性维护，使得 ZSet 支持 O(log N) 时间复杂度的插入、删除和范围查询；哈希表则提供 O(1) 的元素查找与更新操作。通过这两种数据结构的组合，ZSet 能够高效地处理大规模数据集的有序集合操作。

# **Redis 为什么快？**

-   基于内存操作，减少磁盘 I/O。
-   单线程模型，避免上下文切换和锁竞争。

# **Redis的应用场景？**

嗯，Redis主要有五种数据结构，String、Hash、List、Set、ZSet，这几种类型都有在实际生产中用过，String主要是用来做计数器、用户信息、幂等操作、分布式锁等，Hash主要用来存储用户详情信息、字典信息登，List有用来做过最近联系人列表和商品浏览历史，因为它是一个有序的列表而且从头部插入，Set是不重复的集合可以用来做赞、关注列表，ZSet是一个有序集合，用来做排行榜。

-   String: 单值缓存（如用户信息、计数器、分布式锁）。
-   Hash: 对象存储（如用户详细信息）。
-   List: 消息队列（如任务列表、商品浏览历史）。
-   Set: 去重功能（如共同好友、标签）。
-   Sorted Set: 排序功能（如排行榜、延时队列）。
-   Bitmap: 位存储（如用户签到、状态统计）。
-   HyperLogLog: 基数估算（如UV统计）。
-   Geo: 地理位置数据（如附近的人、店铺推荐）。
